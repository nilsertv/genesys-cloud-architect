## Phase 2: MCP Tool + Docs (Slice B — depends on Phase 1)

- [x] 2.1 Create `src/mcp-server/tools/update-flow.ts`: zod schema + `.refine()` (per `design.md` § Zod Schema, **corrected** — see Deviation note below), spawn `deploy-runner --mode update`, reuse `deploy-flow.ts`'s NDJSON parse loop unmodified (duplicated inline, per design decision), map `errorKind` to the 4 distinct messages in `design.md` § Differentiated Error Handling.
  - **Deviation from design.md's Zod Schema (by design, per Slice A's discovery)**: `flowType` is a required field (`z.string().min(1)`, no `.optional()`), not optional-only-for-flowName as design.md's original snippet showed. The `.refine()` only checks `Boolean(flowId) !== Boolean(flowName)` (exactly one of the two identifiers) — `flowType`'s required-ness is enforced by the base schema shape itself, independent of which identifier is used. This matches `updateFlow()`'s real signature in `index.ts` (Slice A), which throws if `opts.flowType` is absent regardless of identifier kind.
  - **Type-level deviation (new, found this session, not previously documented)**: the shared `ToolConfig`/`ToolFactory` type in `src/mcp-server/tools/types.ts` originally constrained `inputSchema: T extends ZodRawShape` (a plain raw shape only — `Record<string, ZodTypeAny>`). A `z.object({...}).refine(...)` instance is a `ZodEffects`, which does NOT structurally satisfy `ZodRawShape` (it has methods/internals, not just field keys). Design.md's claim that "the installed `@modelcontextprotocol/sdk` types `inputSchema` as `ZodRawShapeCompat | AnySchema`" is correct for the **MCP SDK's own `registerTool()`** (verified directly in `node_modules/.pnpm/@modelcontextprotocol+sdk@1.29.0_zod@4.4.3/.../mcp.d.ts`), but this project's own `ToolConfig` wrapper type was narrower than the SDK it wraps. Widened `ToolConfig`/`ToolFactory`'s generic bound from `ZodRawShape` to `ZodRawShape | ZodTypeAny` (new `ToolInputSchema` union type) in `types.ts` so `update-flow.ts` can pass the full refined schema through `inputSchema`. Backward compatible — the 3 existing tools (`flow_dependencies`, `deploy_flow`, `test_bot_flow`) still use raw shapes and are unaffected (verified: `pnpm run build` + targeted `tsc --strict` both clean).
  - **CRITICAL bug found and fixed (post-implementation, fresh-context review pass, empirically verified)**: the `.refine()`-wrapped `inputSchema` (a `ZodEffects` instance) broke MCP `tools/list` introspection. The installed `@modelcontextprotocol/sdk`'s `normalizeObjectSchema()` (`node_modules/@modelcontextprotocol/sdk/dist/esm/server/zod-compat.js`) only reads a top-level `.shape` — present on a plain object shape or a `z.object(...)` instance, but NOT on a `ZodEffects` (the `.shape` lives one level deeper, at `_def.schema.shape`). With the `.refine()`-wrapped schema, `normalizeObjectSchema()` returned `undefined` and the `tools/list` handler fell back to `EMPTY_OBJECT_JSON_SCHEMA` — so `update_flow` was announced to MCP clients (including Claude Code) with **zero declared parameters**, making the tool effectively undiscoverable to any LLM that didn't already know its argument names out of band. Validation via `tools/call` still worked (a fallback path uses the raw `ZodEffects` directly), which is why `tsc --noEmit` and biome lint both stayed green — this is a pure SDK-introspection bug, invisible to type-checking. **Fix**: reverted `inputSchema` to a flat `ZodRawShape` (`{ flowFile, flowId, flowName, flowType, forceUnlock, publish }`, no `.refine()`); moved the "exactly one of `flowId`/`flowName`" cross-field check into the handler as a manual post-parse `if`, following the same pattern already used by `deploy-flow.ts`/`flow-dependencies.ts`, returning two DISTINCT `isError: true` messages (both-given vs. neither-given) rather than one generic message. `flowType` stays required in the flat shape (`z.string().min(1)`, no `.optional()`) since it never needed the `.refine()` in the first place. Correspondingly reverted `src/mcp-server/tools/types.ts`'s `ToolConfig`/`ToolFactory` back to `ZodRawShape`-only (removed the `ToolInputSchema = ZodRawShape | ZodTypeAny` union added earlier in this task) — the widened type is no longer needed and would otherwise leave the door open for another tool to reintroduce the same bug. **Empirically verified** (not just `tsc`/lint, which had already passed before and missed this): instantiated a real `McpServer` + `Client` over `InMemoryTransport.createLinkedPair()`, registered the corrected `update_flow` tool, called `client.listTools()`, and confirmed `inputSchema.properties` now contains all 6 keys (`flowFile`, `flowId`, `flowName`, `flowType`, `forceUnlock`, `publish`) with correct types/descriptions, and `inputSchema.required` correctly lists `["flowFile", "flowType"]`. Also called `client.callTool()` with both "neither identifier given" and "both identifiers given" argument sets and confirmed the two distinct manual-validation error messages fire correctly. `pnpm test` (13/13, unaffected), `tsc --noEmit --strict` (0 errors on touched files), `pnpm run build`, and `pnpm run lint` all re-run clean after the fix.
  - **Post-Slice-A-fix update (this session)**: the `"not-found"` message now also notes the type-mismatch caveat (see 2.6) since `classifyUpdateError()` folds a mismatched `flowType` into `not-found`.
